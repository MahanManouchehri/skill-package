# قالب خروجی

<div dir="rtl">

خروجی Skill با عنوان «طرح API و سناریوها» ارائه می‌شود و از الگوی زیر پیروی می‌کند.

## endpointها

برای هر endpoint، یک بخش مستقل بسازید:

~~~~markdown
### ۱. نام خوانای endpoint — موجود | پیشنهادی

- Method و مسیر: `POST /api/...`
- دسترسی: نقش یا مجوز لازم

#### ورودی‌ها

| محل | نام | نوع | اجباری | نمونه | اعتبارسنجی | توضیح |
| --- | --- | --- | --- | --- | --- | --- |
| body | `user_id` | integer | بله | `42` | شناسهٔ کاربر موجود | کاربری که عملیات برای او انجام می‌شود |

#### رفتار

توضیح کوتاه و قابل مشاهده از اعتبارسنجی، بررسی مجوز، عملیات اصلی و نتیجه.

#### پاسخ موفق — `201 Created`

```json
{
  "data": {
    "id": 123,
    "status": "assigned"
  }
}
```

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `data.id` | integer | شناسهٔ منبع ایجادشده یا تغییرکرده |
| `data.status` | string | وضعیت قابل مشاهدهٔ عملیات |

#### خطاهای قابل انتظار

| Status code | علت | فرمت پاسخ |
| --- | --- | --- |
| `403 Forbidden` | کاربر مجوز لازم را ندارد | مطابق قرارداد خطای پروژه |
| `422 Unprocessable Entity` | ورودی معتبر نیست | مطابق قرارداد خطای اعتبارسنجی پروژه |
~~~~

مقادیر نمونه صرفاً ساختار قالب را نشان می‌دهند. مسیر، نام فیلد، نوع، status code و پاسخ واقعی باید از شواهد همان پروژه به‌دست بیایند.

## سناریوهای ترتیبی

پس از endpointها، برای هر نقش یا هدف یک سناریو بنویسید:

```markdown
## سناریو ۱: اقدامات پشتیبان

1. پشتیبان [هدف گام] را انجام می‌دهد؛ از `[METHOD /path]` استفاده می‌کند؛
   خروجی `[field]` ورودی گام بعدی است؛ نتیجهٔ قابل مشاهده [نتیجه] است.
2. ...
```

برای هر گام، بازیگر، علت اقدام، endpointهای مرتبط، ورودی یا خروجی انتقالی و نتیجهٔ قابل مشاهده را مشخص کنید.

## جمع‌بندی نهایی

در پایان، endpointهای موجود، endpointهای پیشنهادی و تصمیم‌های باز را جداگانه فهرست کنید و برای آغاز پیاده‌سازی، تأیید صریح کاربر را بخواهید.
