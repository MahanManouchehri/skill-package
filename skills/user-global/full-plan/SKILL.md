# طرح API برای فیچر

پیش از شروع کدنویسی هر فیچری که به API یا endpoint نیاز دارد، یک طرح قابل تأیید به فارسی طبیعی و فنی تهیه کن. هدف این است که کاربر پیش از پیاده‌سازی دقیقاً بداند هر endpoint چه می‌گیرد، چه کاری می‌کند، چه برمی‌گرداند و در کدام گام سناریو استفاده می‌شود.

این Skill به‌صورت خودکار برای طراحی یا پیاده‌سازی فیچرهای APIمحور اعمال می‌شود. اگر کاربر عبارت `/full-plan` را فرستاد، آن را درخواست صریح برای اجرای کامل همین جریان بدان؛ حتی اگر درخواست کوتاه یا مبهم باشد.

## پیش‌نیاز بررسی

پیش از نوشتن طرح، فقط منابع لازم را در پروژه بررسی کن: endpointها و routeهای موجود، controller/service مرتبط، request validation، serializer/resource/schema، مجوزها، پاسخ‌ها و مستندات API. بین endpointهای موجود و endpointهای پیشنهادی تمایز صریح بگذار؛ مسیر، پارامتر، پاسخ یا status code را حدس نزن.

- endpointهای موجود را با برچسب «موجود» و بر پایهٔ شواهد پروژه بنویس.
- اگر برای تکمیل فیچر endpoint تازه لازم است، آن را با برچسب «پیشنهادی» بنویس و دلیل نیازش را کوتاه توضیح بده.
- فقط endpointهایی را بیاور که برای سناریوهای درخواستی لازم‌اند. endpointهای نامرتبط را فهرست نکن.
- اگر اطلاعات مهمی در کد یا درخواست کاربر وجود ندارد، آن را «نیازمند تصمیم» اعلام کن؛ آن را به شکل قرارداد قطعی ارائه نکن.

## خروجی اجباری پیش از پیاده‌سازی

خروجی را با عنوان «طرح API و سناریوها» ارائه کن و تا دریافت تأیید کاربر، کدنویسی، تغییر قرارداد API، migration یا هر تغییر اجرایی را شروع نکن.

برای هر endpoint، مستقل و با شماره‌گذاری روشن، دقیقاً این بخش‌ها را بیاور:

1. **نام endpoint:** نام خوانا، method و مسیر دقیق؛ همراه با وضعیت «موجود» یا «پیشنهادی» و سطح دسترسی/نقش لازم در صورت وجود.
2. **پارامترهای ورودی:** پارامترهای path، query، body و header را در مناسب‌ترین قالب (جدول یا JSON) نمایش بده. برای هر مورد نام، نوع، اجباری‌بودن، نمونهٔ مقدار، قواعد اعتبارسنجی و توضیح کاربرد را بنویس. اگر ورودی ندارد، صریحاً بگو «ورودی ندارد».
3. **رفتار endpoint:** در چند جملهٔ کوتاه، ترتیب اصلی پردازش، بررسی مجوز، اعتبارسنجی، منبعی که خوانده یا تغییر می‌کند و نتیجهٔ قابل مشاهده را توضیح بده. جزئیات داخلی را فقط وقتی بیاور که برای مصرف‌کنندهٔ API مهم است.
4. **فرمت دقیق خروجی:** پاسخ موفق را با JSON دقیق و status code نشان بده و برای تک‌تک فیلدهای پاسخ، نوع و کاربرد را توضیح بده. پاسخ‌های خطای قابل انتظار را نیز با status code، علت و فرمت واقعی یا پیشنهادی‌شان بیان کن. اگر پاسخ فعلی پروژه با شواهد قابل تأیید نیست، آن را «نیازمند تصمیم» علامت بزن.

کلیدهای JSON، مسیرها، نام مدل‌ها و اصطلاحات قراردادی را دقیق و دست‌نخورده نگه دار. متن توضیحی را فارسی رسمی، مستقیم و روان بنویس؛ از لحن اداری سنگین، ترجمهٔ لفظی و کلی‌گویی پرهیز کن.

## سناریوهای ترتیبی

پس از فهرست endpointها، سناریوها را به ترتیب اجرای واقعی بنویس. هر سناریو باید یک نقش یا هدف مشخص داشته باشد؛ مثل «سناریو ۱: اقدامات پشتیبان».

برای هر گام سناریو مشخص کن:

- بازیگر چه کاری انجام می‌دهد و چرا؛
- کدام endpoint یا endpointها استفاده می‌شوند؛
- ورودی یا منبع مهم آن گام چیست؛
- خروجی گام چگونه به گام بعدی منتقل می‌شود؛
- نتیجه یا وضعیت قابل مشاهدهٔ گام چیست.

نمونهٔ شکل نوشتن برای سناریوی تیکتینگ:

1. پشتیبان با endpoint فهرست صف، کاربران بدون پشتیبان را در بورد می‌بیند.
2. پشتیبان با endpoint تخصیص، یک کاربر را به خودش اختصاص می‌دهد.
3. پشتیبان با endpoint فهرست تخصیص‌ها، کاربران واگذارشده به خودش را بررسی می‌کند.
4. پشتیبان با endpoint گفت‌وگو، چت یکی از کاربران واگذارشده را باز می‌کند.
5. پشتیبان با endpoint پیام‌ها، تاریخچه را می‌بیند و با endpoint ارسال پیام پاسخ می‌دهد.

این نمونه فقط ساختار سناریو را نشان می‌دهد؛ در طرح واقعی نام endpointها، ورودی‌ها و خروجی‌ها باید با شواهد همان پروژه جایگزین شوند.

## پایان طرح

در انتها، یک جمع‌بندی کوتاه از endpointهای موجود، endpointهای پیشنهادی و تصمیم‌های لازم ارائه کن و تأیید صریح کاربر برای شروع پیاده‌سازی بخواه. پس از تأیید، همان طرح را مبنای کار قرار بده و هر تغییر ضروری در قرارداد API را در مستندات مالک API نیز منعکس کن.
